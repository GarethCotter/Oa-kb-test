# Oxford Abstracts Help Centre

Static help centre for Oxford Abstracts (academic conference / abstract management
software), with a Claude-powered answer layer on search. Rebuilt from the old HubSpot
knowledge base in July 2026.

Live: https://oa-kb-test.vercel.app — deploys automatically from `main`.

---

## Who this is for

The primary reader is a **conference organiser: often middle-aged, not especially
confident with software, arriving mid-task and mildly stressed**. Secondary readers are
participants — submitters, reviewers, committee members, attendees, exhibitors — who
usually arrive once, by a deep link from an organiser, with no context.

Every design decision follows from that. When in doubt: plainer language, bigger targets,
fewer choices, and never a dead end. Boring and predictable is the goal, not clever.

## How it is built

Everything is generated from markdown by `build.py`. **Never edit the generated HTML** —
it will be overwritten on the next build.

```
corpus/               174 article markdown files, one folder per section  <- SOURCE OF TRUTH
corpus-internal/      notes the AI can answer from but that never become public pages
structure/            one JSON per section: intro, "start here" article, groups, next stage
assets/img/           1,326 committed screenshots (WebP) - NOT generated, never deleted
assets/search.js      front-end search: keyword layer + AI answer layer   (hand-written)
assets/article.js     image lightbox + feedback widget                    (hand-written)
api/search.js         two Claude Haiku calls: route, then answer          (hand-written)
api/feedback.js       logs article feedback                               (hand-written)
scripts/update-article.js   describe a change -> Sonnet edits -> pull request
vercel.json           199 redirects from the old HubSpot URLs
redirects.csv         the same map in plain CSV
project/              analysis, checklists and decisions still outstanding

assets/favicon.svg    Oxford Abstracts mark, taken from oxfordabstracts.com (+ apple-touch-icon.png)

# generated by build.py, all committed so Vercel can serve them:
index.html, 404.html, 01-getting-started/ … 14-for-attendees-exhibitors/,
assets/style.css, assets/search-index.json, assets/articles.json
```

Rebuild with:

```bash
python3 build.py     # needs: pip install markdown beautifulsoup4 lxml
```

It deletes and regenerates only the 14 section folders, `index.html`, `style.css`,
`search-index.json` and `articles.json`. It never touches `assets/img`, the
hand-written JS, `api/` or `vercel.json`.

Commit and push, and Vercel redeploys. There is no build step on Vercel — it serves the
committed HTML and runs `api/*.js` as serverless functions.

## The structure, and why

**Two audiences, then the event lifecycle.** The landing page splits organisers from
participants, because their intents are completely different. Organiser sections follow
the order an event actually happens (Getting started → Submissions → Reviewing →
Decisions → Emails → Programme → Registration → Conference platform), so the navigation
doubles as a "what do I do next?" checklist.

**Section pages are guides, not indexes.** Each has a two-sentence orientation, one
"Start here" card, articles grouped by phase with descriptions, and a link to the next
stage. The ordering lives in `structure/*.json` so it can be edited without touching code.

**One canonical page per task.** The old KB had a 20-page FAQ silo and a duplicate
symposia tree; both were dissolved into their topics. Don't reintroduce them.

**Add-ons are separated.** Symposia, Certificates and Multi-stage are separately
purchased, so their content is grouped and badged rather than woven through the core path.

## Search: how the answer layer works

Two Claude Haiku 4.5 calls per question, in `api/search.js`:

1. **Route** — the whole article index (~10k tokens) sits behind a `cache_control`
   breakpoint, so after the first call it bills at the cached rate. Returns up to three
   article paths as JSON.
2. **Answer** — only those articles' text is sent. Returns 2–4 sentences of plain English
   plus optional follow-up questions.

Well under a penny per question. `ANTHROPIC_API_KEY` is set in Vercel's environment
variables and must never reach the browser.

**Failure behaviour is deliberate and load-bearing.** The endpoint returns 200 with a null
answer on any error, and the front end silently falls back to keyword search. The reader
never sees an API error and never sees an empty page. Keep it that way.

The keyword fallback has typo tolerance and a synonym map built from real failing search
terms (deadline, incomplete, template…). Add to `SYNONYMS` in `assets/search.js` when new
vocabulary gaps show up.

`corpus-internal/` notes are routed and answered from, but never cited as sources —
they produce a clean answer with no article link. Nothing customer-specific may go in
them: they surface to any user who asks the right question.

## What `build.py` derives from the prose

Three things are lifted out of the markdown rather than written by hand. All three are
derived from surrounding text, so check the built output when you change the sources.

- **Audience tag.** The "The guidance below is for…" sentence is pulled out of the body
  and rendered as a colour-coded tag under the title on 99 articles — navy organisers,
  teal submitters, plum reviewers, amber attendees. Fourteen HubSpot wordings map onto
  four audiences. The tag's "not you?" link goes to our own landing-page doors; the
  original pointed at the old HubSpot KB every time. Sentences that are *support*
  routing ("If you experience any issues, contact your event administrator") are left in
  the prose deliberately — only "If you are …" is audience routing.
- **Alt text.** Each screenshot sits under the step it illustrates, so the alt comes from
  that step with the imperative lead-in stripped: "Click on the **Create an Account**
  button" → "Screenshot: Create an Account button". 1,342 distinct strings across 1,343
  images. It says *which step* is pictured, not what is on screen — nobody has looked at
  the images.
- **Card descriptions.** A section-page card uses the article's standfirst, falling back
  to `lead_sentence()`. Headings are eligible on purpose: most articles open with a
  descriptive `## Create a striking and visually engaging program.` that is the best
  one-line summary they have.

## Conventions

- **Titles**: sentence case, tasks as gerunds ("Creating a session"), troubleshooting in
  the reader's voice ("If your verification email hasn't arrived"), under ~60 characters.
  Put the words people actually search for *in the title* — that is why one article is
  called "Opening and closing submissions (deadlines)".
- **Voice**: write to the reader as "you". Third person is only correct when it genuinely
  refers to someone else ("controlling what the reviewer can see").
- **Menu paths in bold**: `**Event dashboard → Emails → Edit & Send**`.
- **Frontmatter**: `title`, `section`, `audience`, `plan`, `source_url`, `last_reviewed`,
  and `merged_from` where content was consolidated. Bump `last_reviewed` on every edit.
  `source_url` is provenance — the original HubSpot address — and the redirect check
  resolves it against `vercel.json`. Never rewrite it.
- **`plan:`** must match `project/plan-feature-matrix.md`, which is transcribed from the
  pricing page. Nine articles claimed to be on the free plan and were not.
- **British English throughout.**
- **Screenshots: only at decision points.** Bolded menu paths navigate as well as a
  screenshot of a menu does and never go stale; the existing 1,326 images date from
  2021–2023 and some already show a previous UI. Keep pictures for screens that are
  genuinely confusing or where "you should now see this" reassures. Two or three per
  article, not ten.
- **`corpus-internal/` notes: put the keywords in the first 160 characters.** The
  router sees a note's title plus only that much of its body, so a pricing note whose
  plan names sat lower down was never selected for "how much is the Professional
  Conference Package".
- **No hand-written jump links.** The generated "On this page" box does that job; 380
  hand-made in-page links had rotted across 97 pages before they were removed.

## Gotchas that have already bitten us

1. **`cleanUrls: true`** means Vercel serves `/02-submissions` with no trailing slash, so
   relative links on section pages resolve against the site root. Section-page links must
   be **root-absolute** (`/02-submissions/slug.html`). Article pages are fine with
   relative links. There is a resolution checker in the "Checks worth running" section
   below — use it, not a plain file-exists test.
2. **Silent patch failures.** More than one CSS change was applied to a string that had
   already moved, so it did nothing and nobody noticed until the live site looked wrong.
   Assert that an edit actually changed something, and verify against the built output.
3. **The image lightbox** uses the `hidden` attribute; any `display` rule on `.lightbox`
   overrides it. `.lightbox[hidden]{display:none}` must stay.
4. **`assert { type: 'json' }`** is dead syntax — use `with { type: 'json' }`. `api/` has
   its own `package.json` with `"type": "module"` so functions are not transpiled.
5. **The POPULAR list in `build.py`** now raises if it points at a missing page. It used
   to drop them silently, and the list quietly shrank to two entries after the renames.
6. **Images are committed**, not fetched. The old KB hotlinked everything to HubSpot; when
   HubSpot is cancelled those URLs die. Don't reintroduce remote image URLs.
7. **The build runs on Windows now, and three things broke that Linux hid.** `strftime`
   `%-d` is a glibc extension that *raises* on Windows — it silently reverted every
   "Last reviewed" badge to raw ISO for months behind a bare `except`. Writing a file
   without `encoding='utf-8'` gets cp1252. And the `CSS` string is not raw, so a CSS
   escape like `\2192` is read by **Python** as octal — write `\\2192`.
8. **Derived text is computed from HTML that `enrich_body` has already mutated.**
   `lead_sentence()` used to regex-blank the tags, which left behind the `#` from every
   heading's anchor link and ran on into the next block. Parse it, drop `a.anchor`, and
   work one block at a time.
9. **Anything under `corpus/` is public and answerable.** A file outside a section folder
   gets a source-link path that nothing builds, so search could cite a 404. `build.py`
   now refuses to build rather than emit one. Notes the AI may answer from go in
   `corpus-internal/`; work-lists go in `project/`. Two work-lists had ended up in the
   answer store this way.
10. **Verify against every fragment, not one phrase.** A check for "guidance below is for"
   passed while most of that sentence was still on 87 pages, because the removal had
   stopped at the first full stop inside "(eg.". Assert on each piece, and pin the count
   of legitimate matches so a new break cannot hide behind a known-good one.

## Checks worth running after any change

```bash
python3 build.py
python3 scripts/checks.py      # exits non-zero if anything fails
```

`scripts/checks.py` is the standing suite — ten checks, each one there because the
thing it catches actually happened. It covers link resolution under `cleanUrls`,
links to the old HubSpot KB (which the resolution check structurally cannot see,
because it skips `http`), redirect coverage for every renamed article, the audience
sentence never being left in the prose, alt text being per-image, in-page anchors
resolving, one `<h1>` per page, "Most popular" having seven entries, every section
card having a description, and nothing stray under `corpus/`.

Two things it taught us about writing checks, both learned the hard way:

- **Scope to the article body.** Counting across whole pages caught the footer logo
  and the lightbox's deliberately-empty alt, and reported 180 failures that were the
  chrome working correctly.
- **Tripwire phrases must be unique to the fault.** "please click" was tried as a
  proxy for the audience boilerplate; it occurs in ordinary instructions, and the
  derived alt text repeats those instructions, so it false-positived by design.

The original inline link checker, kept for reference:

```bash
python3 build.py

# every internal link, resolved the way a browser would under cleanUrls
python3 - <<'EOF'
import os, re
from urllib.parse import urljoin
root='.'
def served(p):
    rel='/'+os.path.relpath(p,root).replace(os.sep,'/')
    if rel.endswith('/index.html'): return rel[:-len('/index.html')] or '/'
    return rel[:-5] if rel.endswith('.html') else rel
def tgt(u):
    u=u.split('?')[0].split('#')[0]
    if u in ('/',''): return 'index.html'
    p=u.lstrip('/')
    for c in (p,p+'.html',os.path.join(p,'index.html')):
        if os.path.exists(c): return c
    return None
bad=[]
for d,_,fs in os.walk(root):
    if '.git' in d: continue
    for f in fs:
        if not f.endswith('.html'): continue
        fp=os.path.join(d,f); base=served(fp)
        for h in re.findall(r'(?:href|src)="([^"]+)"',open(fp,encoding='utf-8').read()):
            if h.startswith(('http','#','mailto:','data:')): continue
            if tgt(urljoin(base,h)) is None: bad.append((base,h))
print('would 404 in production:', len(bad))
for b in bad[:10]: print(' ', b)
EOF
```

Also worth eyeballing: that every section card has a description, that the "Most popular"
list still has seven entries, and that no article has two `<h1>`s.
